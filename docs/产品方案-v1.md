# 故事图谱（暂定名）产品方案 v1

> 历史方案，仅作讨论记录。当前设计以 [产品设计规范 v1.0](产品设计规范-v1.0.md) 与 [视觉素材规范 v1.0](视觉素材规范-v1.0.md) 为准；本文中的冲突约定不再作为实施依据。全部文档见 [索引](README.md)。

> 用流程图、关系图谱、地图三种视图，让用户看懂一个故事 / 传记 / 小说。每部作品是一个"章节"。

---

## 1. 定位（对应问题 1-4）

| 项 | 决策 | 理由 |
|---|---|---|
| 核心用户 | **正在读长篇的人**（伴读工具） | 痛点最强、最明确：人物记不住、时间线乱。预览型和复盘型用户是顺带覆盖 |
| 使用场景 | 阅读中随手打开，设定"我读到第 N 章"，查人物、查关系、查地点 | 高频、有粘性 |
| 首要痛点 | 人物太多记不住 > 时间线乱 > 地理搞不清 | 按这个顺序排功能优先级 |
| 设备 | **Web 优先，移动端适配**，不做原生 App | 图谱交互在电脑上体验最好；手机端做简化版（列表 + 单节点图） |

## 2. 内容范围（对应问题 5-9）

- **首批 3 部作品**，刻意覆盖三种类型，验证数据模型通用性：
  1. 《西游记》：公版、体量中等、地点线清晰，作为主打样板
  2. 《奥德赛》：公版、双线叙事、真实地理（地中海），验证真实地图 + 非线性叙事
  3. 《凡人修仙传》：在版权期、超长篇、架空地图、境界体系，验证规模上限和版权规避方案
- **内容生产：LLM 抽取 + 人工审校**。自动化产出初稿，人工修正关系和关键事件。不做众包（冷启动时质量不可控），二期再开放纠错。
- **版权**：只存结构化数据（实体、关系、事件摘要），**不存原文全文**；在版权期作品的节点只放不超过 50 字的摘要 + 章节号，让用户去原平台看原文。
- **传记 vs 小说**：同一套数据模型，传记的地点和时间带真实坐标 / 真实日期，地图视图切换为真实底图。
- **粒度**：作品 → 卷/篇 → 章 → 事件。事件是最小单元，一章可含多个事件。

## 3. 数据模型

五类实体，一类关系边，全部带"首次出现章节"字段，这是剧透控制的基础。

```
Work        作品：标题、作者、类型(小说/传记/史诗)、总章数、地图类型(真实/架空)
Chapter     章节：所属作品、序号、标题、卷
Event       事件：标题、摘要、所属章节、发生地点、参与人物、前因事件[]、后果事件[]
Character   人物：名字、别名[]、阵营、简介、首次出现章节、成长阶段[](如境界)
Location    地点：名字、类型、坐标(真实经纬度 或 架空地图像素坐标)、上级地点
Faction     势力/组织：名字、简介、所属地点
Relation    关系边：源实体、目标实体、类型(师徒/夫妻/敌对/从属/持有...)、
            开始章节、结束章节、描述
```

关键设计：**Relation 带开始/结束章节**，所以图谱可以随进度变化（韩立与南宫婉从陌生 → 道侣）。

## 4. 三种视图（对应问题 10-14）

### 4.1 全局控件：进度轴
- 页面顶部一根滑杆，刻度为章节。用户拖到第 N 章，三个视图只显示 N 章及之前的内容。
- 默认位置：**第 1 章**（零剧透），用户可选"我已读完"看全貌。
- 这是产品最核心的差异点，所有视图围绕它设计。

### 4.2 流程图（事件视图）
- 横向时间轴，节点为事件，边为因果。
- 支持**多泳道**：一条泳道一条叙事线（奥德修斯线 / 忒勒马科斯线；取经队 / 天庭线）。
- 一期只做"叙事顺序"，不做"故事内时间顺序"的切换（《奥德赛》的倒叙先用标注解决，二期再做双模式）。
- 点击事件：弹出摘要、参与人物、地点，可跳转到该节点在关系图和地图上的位置。

### 4.3 关系图谱（人物视图）
- 力导向图，节点为人物和势力，边为关系，颜色区分关系类型。
- **动态**：随进度轴变化，边出现/消失/变色。
- 默认只显示"主要人物"（按出场次数排序取前 30），其余折叠，避免《凡人修仙传》上千人物把图挤爆。
- 搜索人物 → 高亮其一跳邻居。
- 点击两个人物 → 显示两人之间的最短关系路径和相关事件（回答"他们怎么认识的"）。

### 4.4 地图（地点视图）
- 真实世界作品：Leaflet/MapLibre 真实底图 + 标注。
- 架空世界作品：上传一张示意图作为底图，地点为像素坐标标注。
- 叠加**人物轨迹**：选择人物，按章节顺序连线其到过的地点，进度轴控制画到哪。
- 地点点击：该地发生过的事件列表。

### 4.5 第四视图：成长线（二期）
- 对修仙 / 成长类小说：人物境界或身份随章节变化的阶梯图。
- 数据模型已经通过 `Character.成长阶段[]` 预留，一期不做 UI。

## 6. 商业与技术（对应问题 19-20）

- **商业**：一期不考虑变现，先验证留存。方向按优先级：① 与阅读平台合作导流（在版权期作品天然需要跳回原平台）；② 教育版卖学校/出版社（公版名著）；③ 会员解锁全部作品。
- **技术栈**（假设小团队、Web 优先）：
  - 前端：Next.js + TypeScript；图渲染 AntV G6（关系图、流程图，国内文档好）；地图 MapLibre GL（真实）+ Leaflet CRS.Simple（架空底图）
  - 后端：Node/Python 均可，一期数据量小，直接 **PostgreSQL** 存实体和关系，不上图数据库；到几十部作品后再评估 Neo4j
  - 数据抽取流水线：Python 脚本，按章节调用 LLM 抽取 → JSON → 人工审校界面（可先用表格）→ 导入数据库
  - 部署：Vercel + Supabase 或自建

## 8. 待你确认的点

1. 产品名和首批作品选择是否同意
2. "Web 优先、不做原生 App"是否可接受
3. 《凡人修仙传》这种在版权期作品是否要做，还是一期全用公版
4. 技术栈是否与你现有团队匹配（如果你有偏好的语言/框架，告诉我）
5. 里程碑周期是否符合你的资源
